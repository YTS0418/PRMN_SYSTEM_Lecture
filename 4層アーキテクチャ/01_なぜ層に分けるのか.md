## 1. 何でも詰め込んだコード

「学生の成績一覧を表示する」機能を、1 つの処理に全部書くとどうなるでしょうか。入力、検査、データの取得、計算、表示を、すべてプログラムの入口（`main` など）に書いた例です。言語に依存しない**疑似コード**で示します。

```text
処理 成績一覧を表示する():
    学生番号 = 画面（キーボード）から入力を受け取る          // ① 入力を受け取る
    合計 = 0 ; 件数 = 0
    繰り返し 行 in ファイル "enrollments.csv" の全行:         // ② ファイルから読み込む
        (学生番号, 科目名, 点数) = 行をカンマで分割する        //    （学生番号,科目名,点数）
        もし 行の学生番号 ≠ 学生番号 なら 次の行へ             // ③ 学生で絞り込む
        もし 点数 < 0 または 点数 > 100 なら 次の行へ          // ④ 業務ルール（点数の範囲）
        画面に「科目名 : 点数」を表示する                      // ⑤ 表示する
        合計 += 点数 ; 件数 += 1
    画面に「平均: 合計 ÷ 件数」を表示する                      // ⑥ 計算する
```

動きはしますが、この 1 つの処理が、**性質の違う 6 つの仕事**を同時に抱えています。これは Java でも Python でも JavaScript でも、同じように起こります。

| 番号 | 仕事 | 性質 |
|---|---|---|
| ① ⑤ | 入力と表示 | 画面・ユーザーとのやり取り |
| ② | ファイルの読み込み | データの保存先 |
| ③ ⑥ | 絞り込みと平均の計算 | アプリケーションの処理 |
| ④ | 点数は 0〜100 | 業務のルール |

## 2. 困りごと 1：変更が怖い

次のような変更が来たとします。

- **保存先をファイルからデータベースに変えたい** → ② を書き直す。しかし、②と③⑥が絡み合っているので、**計算のコードまで壊すかもしれない**
- **コンソールではなく Web 画面にしたい** → ① ⑤ を書き直す。しかし、表示する処理の中で計算もしているので、**計算ロジックを取り出せない**
- **合格点を 60 点から変えたい** → ルールがあちこちに散らばっていて、**全部探して直す**必要がある

> [!NOTE]
> 1 つの変更理由に対して、**直す場所が 1 か所**であるのが理想です。上のコードでは、直す場所が絡み合っています。

## 3. 困りごと 2：テストできない

「平均点の計算が正しいか」を確かめたいとき、上のコードでは次のようなことをしないとテストできません。

- キーボードから学生番号を入力する
- `enrollments.csv` というファイルを用意する
- 画面に出た文字を目で見て確認する

計算だけをテストしたいのに、**入力・ファイル・表示が一緒についてくる**からです。計算が独立した関数であれば、`average([80, 90])` が `85.0` を返すか、すぐに確かめられます。

## 4. 困りごと 3：分担できない

複数人で開発するとき、全員が同じファイルを編集すると、Git の**コンフリクト**が頻発します（[Git 資料](../Git/02_CUI基本編.md) で学んだ問題です）。

「画面担当」「データベース担当」「業務ロジック担当」で作業を分けたくても、1 つのクラスに全部が入っていると分けられません。

## 5. 関心の分離

困りごとの原因は、**性質の違う仕事（関心事）が 1 か所に混ざっている**ことでした。これを、性質ごとに分けて別々の場所に書く考え方を**関心の分離**（Separation of Concerns）と呼びます。

「1 つの部品（クラスや関数）には 1 つの責任だけを持たせる」という**単一責任の原則**と、同じ発想です（Java での例は [Java 入門 10 章](../付録/Java入門/10_総合演習.md) にあります）。部品単位で責任を分けるのが単一責任の原則、**部品の集まり（層）単位で責任を分ける**のが、この資料の「層構造」です。

> [!NOTE]
> この考え方は、Web アプリ（MVC）、スマートフォンアプリ、Python や Node.js のサーバーなど、**言語や分野を問わず**使われています。この資料の第 1 部（01〜03 章）は言語に依存しない形で説明し、第 2 部（04 章以降）で Java での書き方を扱います。

## 6. 層に分ける

先ほどの 6 つの仕事を、性質ごとに 4 つのグループ（**層**）に分けます。

```mermaid
flowchart TB
    subgraph P["Presentation 層：入力と表示"]
        p1["① 学生番号を入力<br>⑤ 結果を表示"]
    end
    subgraph A["Application 層：処理の流れ"]
        a1["③ 学生で絞り込む<br>⑥ 平均を計算する"]
    end
    subgraph D["Domain 層：業務のルール"]
        d1["④ 点数は 0〜100"]
    end
    subgraph I["Infrastructure 層：保存先"]
        i1["② ファイルから読み込む"]
    end
    P --> A --> D
    I --> D
```

> [!NOTE]
> 矢印は「**依存する**（使う・知っている）」向きです。Application 層は、Infrastructure 層を**直接は呼びません**。それでも ② のファイル読み込みを使える仕組み（Domain 層に置いたインタフェース）は、[03 章](03_依存の向きとインタフェース.md)で説明します。

分けると、先ほどの困りごとはこう変わります。

| 困りごと | 層に分けたあと |
|---|---|
| 保存先をデータベースに変えたい | **Infrastructure 層だけ**を書き換える。他の層は触らない |
| Web 画面にしたい | **Presentation 層だけ**を作り直す。計算は再利用できる |
| 合格点を変えたい | **Domain 層の 1 か所**を直す |
| 平均点をテストしたい | Application 層のメソッドを呼ぶだけ。入力・ファイルは不要 |
| 分担したい | 層ごと（ファイルごと）に担当を分けられる |

## 7. 層に分けるデメリット

層に分けるとよいことばかりではありません。

- **ファイルとクラスが増える**：小さなプログラムでは、かえって読みにくくなる
- **受け渡しのコードが増える**：層の間でデータを渡す書き方が必要になる
- **設計の知識が必要**：「これはどの層に書くのか」を判断する力が要る

> [!TIP]
> 数十行の使い捨てのプログラムなら、層に分ける必要はありません。**長く使う・複数人で作る・変更が入る**アプリケーションで効果を発揮する考え方です。

## 8. よくあるミス

| ミス | 原因・対処 |
|---|---|
| 層の数が「4 つ」であることだけを覚える | 大事なのは**数ではなく、関心を分けること**。次章で各層の「責任」を押さえる |
| とりあえず全部の処理を新しいクラスに移す | 層は「クラスを増やすこと」が目的ではない。**何が変わりやすいか**を基準に分ける |
| 小さなプログラムまで無理に層に分ける | 規模に見合った設計にする |
